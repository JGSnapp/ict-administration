# Отчёт по лабораторной 3 — Kafka для двух сервисов

## Что требовалось

Суть лабораторной: собрать цепочку user-service, Kafka и picker-service. Сервис пользователя должен создавать заказы, Kafka передаёт их дальше, сервис сборщика обрабатывает. Нужно настроить Kafka с нуля через конфигурацию, проверить её поведение в бизнес-ситуациях. Плюс наладить Kafka UI и мониторинг.

## Часть 1. СОздание двух сервисов

Как стек продолжил использовать Docker Compose + Python/Flask по опыту второй лабораторной, чтобы не тратить время на новый стек. По моей просьбе через гпт были созданы два минимальных сервиса:

- user-service: страница с кнопкой «Создать заказ», создаёт order_id, которая показывает подтверждение отправки.
- picker-service: страница ожидания + служебное сообщение в консоль.

На первом же запуске picker-service упал с http 500. Причиной оказался русский текст в print и кодировка виндоус-консоли. Консольные сообщения были заменили на ASCII.

Страницы сервисов (снимки сделаны уже после подключения Kafka):

До контейнеризации еще раз разобрался с базовыми понятиями: топик (именованный журнал сообщений), партиция (часть топика со своей очередью), offset (номер сообщения внутри очереди партиции)

### Топик orders из конфигурации

У официального образа нет переменной для создания именованных топиков, поэтому использован одноразовый init-контейнер на том же образе Kafka: переопределённый entrypoint ждёт брокер и выполняет kafka-topics.sh --create. ГПТ сказал, что это более-менее нормальная практика.

Первая попытка упала с exit code 2: Compose разбил многострочный command: | на несколько аргументов, и в bash -c как программа ушло только слово until. Получилось исправить передачей скрипта одним элементом списка.

![лог создания топика](screenshots/kafka2.png)

Стартовые параметры топика: 1 партиция, replication factor 1 (брокер один), retention 2 дня.

### Подключение клиента

В user-service добавлен клиент confluent-kafka. Настройки вынес в переменные окружения, чтобы адрес и топик можно было менять, по необходимости, без правки кода:

- адрес брокера внутри Compose-сети KAFKA_BOOTSTRAP_SERVERS=kafka:19092
- топик для заказов KAFKA_TOPIC=orders
- добавил depends_on: kafka-init с service_completed_successfully

Обработчик /api/orders сериализует заказ в JSON и отправляет его через produce() и возвращает partition/offset.

Затем разобрался с библиотекой для питона и необходимыми методами:

- produce() кладёт сообщение во внутреннюю очередь клиента, отправкой занимаются фоновые потоки
- flush(10) блокирует вызов, пока все поставленные сообщения не будут доставлены, за счёт этого ответ обработчика делается синхронным


### Подключение сервера

В picker-service настроен confluent_kafka.Consumer:

- подписка на топик orders
- группа потребителей pickers
- auto.offset.reset=earliest заставляет сервис начинать с начала, если сохранённой позиции нет
- добавил синхронный commit() после обработки заказа

Чтение выполняется в фоновом потоке. Последний обработанный заказ отдаётся через /api/status, страница его периодически опрашивает.

Смысл consumer group сначала был понятен не до конца. Он в том, что внутри одной группы партиции делятся между участниками и каждое сообщение обработается один раз на группу, а разные группы получают весь поток независимо.

## Часть 3 — Бизнес-ситуации

### 1. Больше партиций

Перед распродажей ожидается всплеск заказов, и один сборщик может не справиться. Чтобы несколько сборщиков могли обрабатывать заказы одновременно, топику нужно несколько партиций: каждая партиция это отдельная очередь, которую можно отдать отдельному сборщику. Поэтому число партиций увеличил с 1 до 3.

У меня изначально kafka-init создавал топик командой create с флагом --if-not-exists, то есть «создать, только если топика ещё нет». Топик уже существует, поэтому этот флаг просто пропускал создание и ничего не менял. Чтобы конфигурация обновляла существующий топик, в kafka-init добавлена вторая команда --alter --partitions 3, которая выставляет нужное число партиций у уже созданного топика:

![финальный kafka-init с alter](screenshots/kafka-init2.png)

Интересно, что уменьшить число обратно нельзя.

Результат виден в логах брокера: к существующей orders-0 добавились orders-1 и orders-2, retention не изменился. Топик теперь из трёх партиций.

Отдельная деталь: сначала обсуждался более сложный вариант kafka-init, который сверял бы желаемое состояние топика с фактическим и менял бы только то, что расходится. Для учебной лабораторной он оказался избыточным, поэтому ограничились простой схемой create + alter.

### 5. Пересчёт истории: reset offsets к earliest

Аналитикам нужно заново прогнать все заказы с самого начала. В обычной очереди так нельзя, т.к. сообщение после чтения удаляется. Здесь это возможно, т.к. оно остаётся в партиции, а позиция группы это просто закоммиченный offset, который можно сдвинуть.

Порядок был важен: сначала остановлены оба consumers, чтобы группа стала неактивной (reset для активной группы Kafka не выполняет). Группа после остановки:

![группа pickers без активных членов](screenshots/state-empty.png)

Остановил, открыл Reset offsets, выбрал EARLIEST:

![форма reset offsets](screenshots/reset-offset.png)

UI подтвердил сброс:

![успешный reset](screenshots/reset-offset2.png)

После сброса current offsets обнулились (0/0/0), end offsets 10/11/16, total lag стал 37:

![lag 37 после ресета](screenshots/reset-offset3.png)

Сумма end offsets всех трёх партиций. Commit сообщение не удаляет, оно хранится до retention, поэтому вся история снова читаема.

После запуска сборщиков группа снова STABLE, current = end, lag 0, а в логах ровно 37 строк Processed, включая самый первый offset 0 и контрольный order-4cebb4d6:

![группа после перепроигрывания истории](screenshots/reset-offset4.png)

Вся история подтянулась, ничего не потерялось.

### 6. Диск заполняется старыми заказами: retention

Заказы нужны пару дней, а копятся бесконечно, значит retention надо уменьшать. Для наглядности временно выставлены через настройки топика в Kafka UI retention.ms=30000 (30 секунд) и кастомный параметр segment.ms=10000:

![настройки топика до](screenshots/settings1.png) ![ретеншн 30с и segment.ms 10с](screenshots/settings2.png)

Зачем segment.ms: Kafka удаляет закрытые сегменты целиком, а не отдельные сообщения. С малым segment.ms сегмент быстрее закрывается и становится кандидатом на удаление, иначе ждать пришлось бы минуту при стандартном segment.roll.ms.

Созданы контрольные заказы, состояние до: 40 сообщений в UI, включая уже прочитанные группой:

![сообщения до очистки](screenshots/retention-before.png)

После истечения срока и периодической чистки Kafka:

![после retention — пусто](screenshots/retention-after.png)

No messages found. Это значит, что все 40 сообщений, включая уже прочитанные, были удалены политикой хранения. Затем возвращены рабочие настройки, то есть retention.ms выставлен 172800000 и segment.ms убран.

Проверил, что lag рисуется: сборщики остановлены, создано пять заказов, на графике Pickers lag виден скачок примерно до 27, после их запуска lag вернулся к нулю. Brokers стабильно 1, under-replicated partitions 0.

Три метрики для алертов и их смысл:

1. kafka_brokers < N: упал брокер. Без брокера не работает ни producer, ни consumer, обработка заказов останавливается целиком
2. kafka_consumergroup_lag_sum: растет, если потребители не успевают или недоступны, заказы копятся необработанными. При этом lag может расти и без падения consumers, если producers внезапно стали быстрее
3. kafka_topic_partition_under_replicated_partition > 0: часть назначенных реплик недоступна
